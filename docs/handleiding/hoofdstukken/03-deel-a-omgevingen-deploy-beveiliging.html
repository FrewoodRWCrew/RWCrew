Omgevingen: lokaal, test en productie

Iedereen
RWCrew draait op drie plaatsen. Lokaal op de pc van een ontwikkelaar (database in Docker, backend en frontend rechtstreeks gestart). Test op test.rwcrew.eu en productie op rwcrew.eu, allebei op dezelfde Hostinger-server, elk in een eigen map, met een eigen database, eigen instellingen en eigen poorten. Test volgt de Git-branch develop, productie volgt main.

De lokale ontwikkelomgeving

Lokaal draaien de onderdelen iets anders dan op de server: alleen de database draait in Docker, backend en frontend worden rechtstreeks gestart. Zo kun je de code aanpassen en meteen het resultaat zien. toont de opstelling, inclusief de manieren om een echte telefoon te laten meedoen.

Dagelijks opstarten

Open daarna http://localhost:3000. Je wordt doorgestuurd naar /nl/login. De interactieve API-documentatie staat op http://localhost:8020/docs.

Start de backend niet met --reload. Op Windows laat die optie bij het stoppen een "weesproces" achter dat de poort blijft bezetten met de oude code. Het gevolg: verzoeken gaan willekeurig naar de oude of de nieuwe versie en fouten lijken "niet opgelost" terwijl ze dat wel zijn. Dit heeft in het verleden veel tijd gekost. Herstart de backend gewoon met de hand na een wijziging. Zie voor de volledige uitleg en hoe je zo'n proces opspoort.

Testen op een echte telefoon

Er zijn twee manieren om de lokale versie op een telefoon te openen:

  • Via wifi (eenvoudig, maar zonder camera en GPS): zorg dat telefoon en pc op hetzelfde wifi-netwerk zitten, zoek het IPv4-adres van de pc op (Get-NetIPAddress, interface "Wi-Fi") en open http://<dat-adres>:3000/m.
  • Via een Cloudflare-tunnel (met camera en GPS, want HTTPS): start cloudflared tunnel --url http://localhost:3000 en open het getoonde adres https://<naam>.trycloudflare.com/m op de telefoon. Het adres verandert bij elke start.

Beide werken alleen als in frontend/.env.local deze twee regels staan (in plaats van een vast backend-adres), omdat de browser dan alle API-verzoeken naar het adres stuurt waarop de pagina geopend werd, en de frontend ze doorgeeft aan de backend:

Zet het tunneladres nooit in NEXT_PUBLIC_API_URL. Inloggen op localhost mislukt dan stilzwijgend: de inlogcookie wordt voor het tunneladres gezet en het loginscherm komt zonder foutmelding terug. Om dezelfde reden moeten het adres van de frontend en NEXT_PUBLIC_API_URL altijd dezelfde hostnaam gebruiken (localhost en 127.0.0.1 gelden als verschillende sites).

De server (Hostinger VPS)

Test en productie draaien op één VPS (Virtual Private Server) bij Hostinger, met Ubuntu Linux en Docker. Op de server staan twee volledig gescheiden kopieën van de repository:

  • /opt/rwcrew/test: volgt develop, bereikbaar via test.rwcrew.eu;
  • /opt/rwcrew/production: volgt main, bereikbaar via rwcrew.eu.

Elke map heeft een eigen .env-bestand met eigen wachtwoorden en sleutels, en wordt gestart als een eigen docker compose-project. Daardoor hebben test en productie elk hun eigen drie containers (db, backend, frontend) en hun eigen opslag (volumes), en kunnen ze elkaar nooit hinderen. Beide gebruiken hetzelfde bestand docker-compose.prod.yml.

De containers luisteren alleen op het interne adres 127.0.0.1 van de server; ze zijn niet rechtstreeks vanaf het internet bereikbaar. Alleen Nginx luistert naar buiten (poorten 80 en 443). De configuratie staat in deploy/nginx/rwcrew.conf:

Hoe Nginx verzoeken verdeelt

HTTPS-certificaten worden aangevraagd en automatisch vernieuwd door certbot. Certbot herschrijft het Nginx-bestand op de server en voegt aparte blokken voor poort 443 toe.

Nginx weigert standaard verzoeken groter dan 1 MB. Daarom zet de configuratie client_max_body_size 25m op het TagScan-adres. Na een certbot-wijziging moeten die regel en de snelheidslimiet (limit_req) ook in de 443-blokken staan, anders worden grote CSV-bestanden van de Raspberry Pi geweigerd voordat de backend ze ziet.

De volledige installatie van de server (gebruikers, firewall, Docker, Nginx, certbot, GitHub-sleutels) staat stap voor stap in docs/deploying-to-hostinger.pdf.

De database bekijken (pgAdmin)

Om een probleem op test of productie te onderzoeken, kun je de database bekijken met pgAdmin op je eigen pc. De database is nooit rechtstreeks via het internet bereikbaar; pgAdmin maakt daarom eerst een beveiligde SSH-tunnel naar de server en logt dan in met de gebruiker rwcrew_readonly, die alles kan lezen maar niets kan wijzigen.

Geef de productieserver in pgAdmin een rode achtergrondkleur. Zo weet je altijd zeker dat je naar de echte gegevens kijkt.

Back-ups: aandachtspunt

In de repository staat geen script dat automatisch back-ups van de databases maakt. De gegevens staan in Docker-volumes op de VPS. Spreek als team af hoe back-ups geregeld worden en leg dat vast, bijvoorbeeld:

  • controleren of de automatische snapshots van Hostinger aan staan en hoe lang ze bewaard worden;
  • een dagelijkse pg_dump van de productiedatabase (via cron) naar een opslag buiten de server;
  • minstens één keer per seizoen een terugzetting proberen op test, zodat je weet dat de back-up werkt.

Hetzelfde geldt voor het volume met TagScan-bestanden (tagscan_data).

Deployment en CI/CD

Iedereen
Een nieuwe versie online zetten gebeurt automatisch. Elke push naar develop zet die versie binnen enkele minuten op test.rwcrew.eu; elke push naar main zet ze op rwcrew.eu. GitHub Actions logt daarvoor in op de server en voert het script deploy/scripts/deploy.sh uit: code ophalen, containers opnieuw bouwen en starten, databasemigraties uitvoeren. Er is dus geen aparte "release"-knop. Wat in main staat, staat in productie.

Van commit tot live

GitHub Actions

De map .github/workflows/ bevat twee workflows: deploy-test.yml (start bij een push naar develop) en deploy-production.yml (start bij een push naar main). Ze doen allebei één ding: met SSH inloggen op de VPS en deploy.sh uitvoeren in de map van die omgeving. De inloggegevens staan als secrets in de GitHub-repository (Settings > Secrets and variables > Actions):

GitHub-secrets voor de deployment
SecretInhoud
SSH_HOSTIP-adres of hostnaam van de VPS
SSH_USERDe gebruiker waarmee gedeployed wordt
SSH_PRIVATE_KEYDe private SSH-sleutel van die gebruiker (de publieke sleutel staat op de server)

Je volgt een deployment op GitHub onder het tabblad Actions. Een groen vinkje betekent dat het script zonder fout liep; bij een rood kruis zie je daar de foutmelding.

Wat deploy.sh doet

  1. Code ophalen. --ff-only weigert als er op de server lokale wijzigingen staan. Wijzig op de server dus nooit code met de hand.
  2. Bouwen en starten. Docker bouwt alleen de containers opnieuw waarvan iets veranderd is en vervangt ze. Tijdens het herstarten is de site enkele seconden onbereikbaar.
  3. Migraties. Nieuwe databasemigraties worden uitgevoerd in de backend-container. Een migratie die faalt, laat de deployment falen (rood kruis in GitHub Actions).
  4. Opruimen. Oude, ongebruikte Docker-images worden verwijderd zodat de schijf niet volloopt.

De Docker-images

  • Backend (backend/Dockerfile): vertrekt van python:3.14-slim, installeert requirements.txt, kopieert de code en start uvicorn app.main:app op poort 8020.
  • Frontend (frontend/Dockerfile): bouwt in drie stappen (pakketten installeren, de app bouwen met npm run build, een kleine eindcontainer met alleen het resultaat) op basis van node:22-slim. Next.js staat op output: "standalone", zodat de eindcontainer klein blijft.
  • Database: het officiële image postgres:16, zonder aanpassingen.
Variabelen die met NEXT_PUBLIC_ beginnen, worden tijdens npm run build in de JavaScript voor de browser ingebakken. Ze worden daarom als build-argument aan de frontend-container gegeven (args: in docker-compose.prod.yml) en niet als gewone omgevingsvariabele. Wijzig je zo'n waarde in de .env van de server, dan moet de frontend opnieuw gebouwd worden; herstarten is niet genoeg.

Een nieuwe instelling toevoegen

docker-compose.prod.yml geeft de backend een expliciete lijst van omgevingsvariabelen (environment:). Een nieuwe instelling die alleen in de .env van de server staat, komt niet in de container terecht. Dat is de reden dat de eerste test-deployment geen mails verstuurde.

Een nieuwe backend-instelling toevoegen gaat dus altijd in vier stappen:

  1. het veld toevoegen aan Settings in backend/app/core/config.py (met standaardwaarde en commentaar);
  2. de variabele toevoegen aan de environment:-lijst van de backend in docker-compose.prod.yml;
  3. de variabele met uitleg toevoegen aan .env.test.example, .env.production.example en backend/.env.example;
  4. de echte waarde invullen in de .env op de server, in beide mappen, en de backend herstarten (docker compose -f docker-compose.prod.yml up -d backend).

Een slechte versie terugdraaien gebeurt via Git, niet op de server: maak een git revert van de foute commit(s) en push die naar main (en develop). Checklist voor een release naar productie

  • Alle backend-tests slagen lokaal (pytest) en de frontend bouwt zonder fouten (npm run build, npm run lint).
  • De wijziging staat op develop en is op test.rwcrew.eu door een tweede persoon gecontroleerd.
  • Nieuwe instellingen zijn op de productieserver ingevuld (zie ).
  • Bevat de release een migratie die gegevens wijzigt of verwijdert? Dan is er vlak voordien een back-up gemaakt.
  • Het moment is gekozen: niet tijdens een festival of een drukke periode, tenzij het een dringende oplossing is.
  • Na de deployment: GitHub Actions is groen, https://rwcrew.eu/api/health antwoordt, en de gewijzigde schermen werken.
  • De handleiding en CLAUDE.md zijn bijgewerkt als de werking veranderde.

Beveiliging en toegangsrechten

Iedereen
Wie mag wat in RWCrew, wordt op twee onafhankelijke niveaus bepaald. (1) Moduletoegang: de superbeheerder beslist per gebruiker welke modules die mag openen. (2) Rechten binnen een module: de beheerder van die module bepaalt met zelfgemaakte rollen wat iemand per scherm mag zien, aanmaken, wijzigen of verwijderen. Je hebt beide nodig. Inloggen gebeurt met e-mail en wachtwoord; de sessie blijft maximaal 6 uur geldig. Alle controles gebeuren in de backend.

Inloggen en wachtwoorden

  • Wachtwoorden worden nooit bewaard, alleen een hash met PBKDF2-HMAC-SHA256, een willekeurige salt per wachtwoord en 260.000 herhalingen. Dat maakt het raden van wachtwoorden uit een gestolen database zeer traag. Code: backend/app/core/security.py.
  • Bij een fout e-mailadres en bij een fout wachtwoord geeft de backend exact dezelfde foutmelding, zodat niemand kan uitzoeken welke e-mailadressen bestaan.
  • Elke inlogpoging, geslaagd of niet, komt in de inloghistoriek (Landing_login_history): tijdstip, e-mailadres, IP-adres, of het via de website (web) of de telefoon-app (pwa) was, en het soort toestel (pc, telefoon, tablet).
  • Een gebruiker kan zijn eigen wachtwoord wijzigen (huidig wachtwoord vereist). Daarbij worden al zijn andere sessies (andere browsers, telefoon) beëindigd.
  • De superbeheerder kan in Manage Access het wachtwoord van een gebruiker resetten (alle sessies van die gebruiker worden dan beëindigd) of een account verwijderen. Een account met is_active uit kan niet inloggen en wordt bij elk verzoek geweigerd; daar is nog geen knop voor in de interface.

Sessies: toegangstoken en vernieuwingstoken

Na het inloggen krijgt de browser twee cookies, allebei HttpOnly (JavaScript in de pagina kan ze niet lezen, wat diefstal via kwaadaardige code bemoeilijkt) en SameSite=Lax (ze worden niet meegestuurd met verzoeken die vanaf andere websites vertrekken):

De twee inlogcookies
CookieGeldigDoel
rwcrew_access_token15 minutenBewijst bij elk verzoek wie je bent.
rwcrew_refresh_tokentot 6 uur na inloggenAlleen om een nieuw toegangstoken te halen (POST /api/auth/refresh).

Waarom zo? Een kortlevend toegangstoken beperkt de schade als het ooit onderschept wordt. Het vernieuwingstoken zorgt ervoor dat de gebruiker toch niet elk kwartier moet inloggen. De harde grens van 6 uur na het ingeven van het wachtwoord zorgt ervoor dat er geen sessies dagenlang open blijven staan, en dat de inloghistoriek echte, recente logins toont.

Elke keer dat het vernieuwingstoken gebruikt wordt, wordt het vervangen door een nieuw (rotatie) en wordt het oude ongeldig gemaakt. In de database staat alleen een hash van elk vernieuwingstoken (Landing_refresh_tokens). Een oud, al gebruikt token dat nog eens opduikt, wordt geweigerd.

Het stil vernieuwen gebeurt op twee plaatsen in de frontend, en beide zijn nodig:
  1. frontend/src/proxy.ts: bij het openen van een pagina met wel een vernieuwings- maar geen toegangscookie vraagt de proxy eerst nieuwe tokens aan (via lib/session-refresh.ts), nog vóór de pagina opgebouwd wordt. Server Components kunnen zelf geen cookies zetten, dus dit kan niet later gebeuren.
  2. frontend/src/lib/api.ts, functie fetchWithRefresh: bij een 401-antwoord op een verzoek vanuit de browser wordt één keer vernieuwd en het verzoek herhaald.
Omdat de backend het vernieuwingstoken bij elk gebruik roteert, mag er per token maar één vernieuwing tegelijk lopen; een tweede gelijktijdige poging met hetzelfde token krijgt een 401. Beide plaatsen delen daarom één lopende vernieuwing (single-flight) en de proxy onthoudt het resultaat 30 seconden. Behoud dat als je hier iets aanpast. Elk token bevat ook een willekeurige jti; zonder die waarde zouden twee tokens die in dezelfde seconde voor dezelfde gebruiker gemaakt worden identiek zijn, en zou de rotatie stilzwijgend falen. Verwijder die niet.

Twee onafhankelijke toegangsniveaus

Niveau 1: moduletoegang

De superbeheerder (een gebruiker met is_super_admin) beslist op het scherm Manage Access per gebruiker welke modules die mag openen. Dat is een eenvoudig vinkje per module, bewaard in Landing_user_module_access. Een module zonder vinkje verschijnt niet op het startscherm, en elk endpoint van die module antwoordt met 403.

Superbeheerder zijn geeft niet automatisch toegang tot de modules, ook niet tot de eigen modules. Dat is een bewuste keuze: de macht van de superbeheerder is beslissen wie wat mag openen, niet alles zien. Wil de superbeheerder zelf een module openen, dan zet die bij zichzelf het vinkje, zoals voor iedereen. Code: backend/app/shared/access.py.

Niveau 2: rollen met rechten per scherm

Binnen modules 1, 2, 3, 8 en 9 bepaalt een rollensysteem wat iemand mag. Elke module heeft daarvoor een eigen menu Access Rights met twee schermen:

  • Roles: rollen aanmaken (vrij te kiezen namen, bv. "Kernlid", "Logistiek", "Lezer") en per rol een rechtenmatrix invullen: per scherm van de module vier vinkjes, view (zien), create (aanmaken), edit (wijzigen) en delete (verwijderen).
  • Users: per gebruiker met moduletoegang één rol kiezen, en nieuwe gebruikers rechtstreeks toegang geven tot deze module.

Belangrijke regels van dit systeem:

  • Geen vinkje is geen recht. Een nieuw scherm verschijnt automatisch als lege rij in elke rechtenmatrix; niemand kan er iets tot een beheerder een rol aanvinkt. Veilig standaard.
  • Eén rol per gebruiker per module. Wil je iemand meer rechten geven, pas dan zijn rol aan of maak een nieuwe rol.
  • Schermen zijn onafhankelijk. Recht op het ene scherm zegt niets over een ander scherm. Ook de schermen Roles en Users zijn apart: iemand kan gebruikers toevoegen zonder rollen te mogen aanpassen.
  • De superbeheerder mag binnen een module alles, op voorwaarde dat hij moduletoegang heeft. Zo kan hij de allereerste rol van een module aanmaken, of ingrijpen als de enige modulebeheerder vertrekt.
  • Een rol toekennen kan alleen aan iemand die al moduletoegang heeft.

Modules met vaste rollen

Modules 4 tot 7 en module 10 gebruiken nog een eenvoudiger, ouder systeem: drie vaste rollen (admin, editor, reader) in één gedeelde tabel Landing_module_roles. Zodra zo'n module echte inhoud krijgt, krijgt ze normaal ook het systeem met rollen per scherm (zie ).

Extra regels in Altsien Select

Altsien Select heeft bovenop de rechten per scherm twee extra regels:

  • Ploegafbakening. Een gebruiker ziet alleen de ploegen waaraan hij gekoppeld is als Altsien-kernlid (MasterData_team_kernlid). Een rol met "zien" op het speciale scherm altsienselect.allteams ("All teams (organisation)") ziet alle ploegen. Een andere ploeg opvragen geeft 404, zodat je niet eens kunt achterhalen dat ze bestaat.
  • Seizoensslot. Zodra bij een seizoen periode_open uit staat, weigert de backend elke wijziging (403), behalve voor wie "wijzigen" heeft op altsienselect.allteams.

Overige maatregelen

  • HTTPS op alle publieke adressen (Let's Encrypt).
  • CORS: de backend accepteert browserverzoeken alleen vanaf de eigen website(s) (CORS_ALLOWED_ORIGINS).
  • Database en containers alleen intern: alleen Nginx is van buitenaf bereikbaar. Voor debuggen is er een read-only databasegebruiker via een SSH-tunnel.
  • Geheimen buiten Git: .env-bestanden staan in .gitignore. De JWT_SECRET is per omgeving verschillend, zodat een token van test nooit op productie werkt.
  • Mails falen veilig: een probleem bij het versturen wordt gelogd maar maakt de bewerking (bv. het opslaan van een aanvraag) nooit ongedaan.
Wie toegang heeft tot de server, de GitHub-repository-instellingen, Hostinger, Cloudflare of Resend, heeft feitelijk toegang tot alles. Houd bij wie welke toegang heeft, geef ze alleen aan wie ze nodig heeft, en wijzig sleutels en wachtwoorden als iemand het team verlaat (zie ).
