Doelgroep: iedereen

Hoe lees je deze handleiding

Iedereen
RWCrew is door één persoon gebouwd en wordt voortaan door een team onderhouden. Deze handleiding legt vast wat tot nu toe vooral in één hoofd zat: hoe de applicatie in elkaar zit, met welke tools ze gemaakt is, hoe je ze lokaal opstart, hoe ze op de server terechtkomt en welke afspraken er in de code gelden. Ze is geschreven voor IT-minded lezers die niet allemaal ontwikkelaar zijn: elk technisch begrip wordt uitgelegd voordat het gebruikt wordt.

Waarom deze handleiding

Een applicatie die door één persoon gebouwd is, heeft een groot risico: de kennis over waarom iets zo gebouwd is, zit niet in de code maar in het hoofd van die persoon. Zolang die persoon beschikbaar is, is dat geen probleem. Zodra meerdere mensen de applicatie moeten beheren, wordt het dat wel. Dan moet iemand anders een fout kunnen oplossen, een nieuwe gebruiker kunnen toevoegen of een nieuwe module kunnen bouwen zonder telkens te moeten vragen hoe het zit.

Deze handleiding heeft daarom drie doelen:

  1. Overzicht geven: in een paar uur lezen moet je begrijpen uit welke onderdelen RWCrew bestaat, hoe die met elkaar praten en waar ze draaien.
  2. Keuzes verklaren: bij elke technologie en elk patroon staat waarom het gekozen is. Zo kun je later een bewuste beslissing nemen om iets te veranderen, in plaats van per ongeluk een zorgvuldig opgeloste valkuil opnieuw open te breken.
  3. Zelfstandig laten werken: met de recepten in en de beheertaken in kun je de meest voorkomende taken uitvoeren zonder hulp.

Basisbegrippen: hoe een webapplicatie werkt

Iedereen
Een webapplicatie bestaat uit drie lagen: de browser van de gebruiker (wat je ziet), een server die de regels toepast (wie mag wat, wat wordt bewaard) en een database waarin alle gegevens blijven staan. De lagen praten met elkaar via vraag-en-antwoordberichten over het internet. Dit hoofdstuk legt die begrippen uit, samen met wat je moet weten over inloggen, beveiliging, broncode, Git en het online zetten van een nieuwe versie. Als je dit al kent, kun je meteen doorgaan naar .

Drie lagen: browser, server, database

Bijna elke moderne zakelijke applicatie, en zeker RWCrew, volgt dezelfde basisopbouw:

  • De browser (Edge, Chrome, Safari) op de pc of telefoon van de gebruiker toont schermen, knoppen en formulieren. De browser zelf bewaart geen bedrijfsgegevens: hij vraagt ze op wanneer hij ze nodig heeft en vergeet ze weer zodra je het venster sluit.
  • De server is een computer die altijd aan staat, ergens in een datacenter. Op die server draaien programma's die verzoeken van browsers ontvangen, controleren of de gebruiker het verzoek mag doen, de juiste gegevens ophalen of wegschrijven en een antwoord terugsturen.
  • De database is het geheugen van de applicatie: een programma dat gegevens netjes in tabellen bewaart, ook als de server herstart. Alleen de server praat met de database; een browser kan nooit rechtstreeks in de database kijken.
Denk aan een restaurant. De browser is de klant aan tafel met de menukaart. De server is de ober en de keuken: die neemt de bestelling op, controleert of het gerecht bestaat en of de klant het mag bestellen, en brengt het bord. De database is de voorraadkamer. Een klant loopt nooit zelf de voorraadkamer in.

Vraag en antwoord: HTTP

Browser en server praten met elkaar via HTTP (HyperText Transfer Protocol), de "taal" van het web. Elk gesprek bestaat uit precies één verzoek (request) van de browser en één antwoord (response) van de server. Een verzoek bevat:

  • een adres (URL), bijvoorbeeld https://rwcrew.eu/api/modules/module-3/intervention-requests;
  • een methode die zegt wat je wilt doen (zie );
  • eventueel gegevens, bijvoorbeeld de ingevulde velden van een formulier;
  • cookies: kleine stukjes tekst die de browser automatisch meestuurt, bijvoorbeeld het bewijs dat je ingelogd bent (zie ).

Frontend en backend

De software die op de server draait, wordt in twee grote stukken verdeeld:

  • De frontend is alles wat met tonen te maken heeft: de schermen, menu's, tabellen en formulieren. In RWCrew is dat een programma geschreven met Next.js (JavaScript/TypeScript). Het maakt de webpagina's die naar de browser gaan.
  • De backend is alles wat met regels en gegevens te maken heeft: wie mag inloggen, wie mag wat zien, wat wordt er in de database bewaard, welke mail wordt verstuurd. In RWCrew is dat een programma geschreven met FastAPI (Python).

Die scheiding is bewust. De frontend mag nooit zelf beslissen of iemand iets mag. Wie technisch handig is, kan in zijn browser alles aanpassen wat de frontend toont, inclusief verborgen knoppen zichtbaar maken. Daarom controleert de backend bij elk verzoek opnieuw of de gebruiker het recht heeft. Een verborgen knop in de frontend is gebruiksgemak; de echte beveiliging zit altijd in de backend.

API, endpoints en JSON

De backend biedt een API aan (Application Programming Interface): een vaste lijst van adressen waarop de frontend vragen kan stellen. Elk zo'n adres, samen met zijn methode, heet een endpoint. Voorbeelden uit RWCrew:

  • POST /api/auth/login: inloggen met e-mailadres en wachtwoord;
  • GET /api/auth/me: "wie ben ik en welke modules mag ik openen?";
  • GET /api/modules/module-3/intervention-requests: de lijst van interventie-aanvragen.

De gegevens die heen en weer gaan, staan in JSON-formaat (JavaScript Object Notation): een eenvoudig, leesbaar tekstformaat van namen en waarden. Zo ziet het antwoord van /api/auth/me er bijvoorbeeld uit:

Database, tabellen en migraties

RWCrew gebruikt PostgreSQL, een veelgebruikte, gratis en zeer betrouwbare relationele database. "Relationeel" betekent dat gegevens in tabellen staan (zoals werkbladen in Excel) die naar elkaar verwijzen:

  • Een tabel bevat één soort gegevens, bv. Landing_users (gebruikers) of InterventionRequests_request (aanvragen).
  • Een rij is één exemplaar (één gebruiker, één aanvraag); een kolom is één eigenschap (e-mailadres, aanmaakdatum).
  • Elke rij heeft een unieke sleutel (id). Een kolom die naar de sleutel van een andere tabel verwijst, heet een vreemde sleutel (foreign key). Zo verwijst een aanvraag via team_id naar een ploeg in MasterData_team.

De taal waarmee je een database bevraagt, heet SQL. In RWCrew schrijf je zelden rechtstreeks SQL: de bibliotheek SQLAlchemy vertaalt Python-code naar SQL (zie ).

Wanneer de structuur van de database verandert, bijvoorbeeld een nieuwe tabel of een extra kolom, gebeurt dat via een migratie: een klein script dat de wijziging beschrijft (en hoe je ze terugdraait). Migraties worden genummerd en in volgorde uitgevoerd, op elke omgeving. Zo heeft de database lokaal, op test en op productie altijd exact dezelfde structuur, zonder dat iemand met de hand tabellen aanmaakt. RWCrew gebruikt daarvoor de tool Alembic (zie ).

Een migratie is als een verbouwingsplan voor een huis: "voeg een raam toe in de keuken". Elk plan bouwt voort op het vorige. Door alle plannen in volgorde uit te voeren, ziet elk huis (elke omgeving) er uiteindelijk hetzelfde uit, en de bewoners (de gegevens) blijven gewoon wonen tijdens de verbouwing.

Inloggen: wachtwoorden, cookies en tokens

HTTP heeft geen geheugen: elk verzoek staat op zichzelf. De server weet dus niet vanzelf dat het verzoek van daarnet en dat van nu van dezelfde persoon komen. Daarom werkt inloggen zo:

  1. Je typt je e-mailadres en wachtwoord. De backend vergelijkt het wachtwoord met de opgeslagen hash: een onomkeerbare "vingerafdruk" van het wachtwoord. Het wachtwoord zelf wordt nooit bewaard.
  2. Klopt het, dan maakt de backend een token: een digitaal ondertekend bewijsje met daarin "dit is gebruiker 12, geldig tot 14u15". Niemand kan dat bewijsje vervalsen zonder de geheime sleutel van de server.
  3. De backend geeft het token mee als cookie. De browser bewaart die cookie en stuurt hem vanaf dan automatisch mee met elk verzoek naar dezelfde website.
  4. Bij elk volgend verzoek leest de backend de cookie, controleert de handtekening en weet zo wie je bent.

RWCrew gebruikt twee tokens: een kortlevend toegangstoken (15 minuten) en een vernieuwingstoken dat de sessie tot maximaal 6 uur na het inloggen verlengt. Hoe dat precies werkt en waarom, staat in . Het type token heet JWT (JSON Web Token), een open standaard.

Domeinnamen, HTTPS en de reverse proxy

Een domeinnaam zoals rwcrew.eu is een leesbare naam voor het IP-adres van een server. Het systeem dat namen naar adressen vertaalt, heet DNS. Voor RWCrew wordt DNS beheerd bij Cloudflare.

HTTPS is HTTP met versleuteling: niemand onderweg (bv. op een openbaar wifi-netwerk) kan meelezen of iets aanpassen. Daarvoor heeft de server een certificaat nodig. RWCrew gebruikt gratis certificaten van Let's Encrypt, die automatisch vernieuwd worden door het programma certbot. Moderne browsers geven sommige functies alleen vrij op HTTPS, zoals de camera (voor het scannen van QR-codes) en GPS. Dat speelt een rol bij de telefoon-app (zie ).

Op de server staat een reverse proxy (Nginx) als portier vooraan. Alle verkeer van buitenaf komt eerst bij Nginx binnen. Nginx regelt de versleuteling en stuurt elk verzoek door naar het juiste programma: adressen die met /api/ beginnen naar de backend, al de rest naar de frontend.

Broncode, Git en GitHub

De broncode is de tekst die ontwikkelaars schrijven en waaruit de applicatie gebouwd wordt. Ze staat in een repository ("repo"): een map met alle bestanden plus hun volledige geschiedenis. Die geschiedenis wordt bijgehouden door Git. De centrale kopie van de repository staat op GitHub.

Van code naar draaiende site: bouwen, containers en deployen

Broncode kan niet zomaar op een server "staan". Ze moet eerst gebouwd worden (de frontend wordt omgezet naar geoptimaliseerde bestanden) en dan gestart worden met de juiste instellingen. Het hele proces om een nieuwe versie live te zetten, heet deployen.

RWCrew gebruikt daarvoor Docker. Docker verpakt een programma samen met alles wat het nodig heeft (de juiste Python- of Node.js-versie, bibliotheken, instellingen) in een container. Een container draait overal precies hetzelfde: op een ontwikkel-pc en op de server. Het recept voor een container staat in een Dockerfile; welke containers samen een applicatie vormen, staat in een docker-compose-bestand.

Een container is als een zeecontainer: wat erin zit maakt voor de haven (de server) niet uit, de afmetingen en de manier van stapelen zijn altijd hetzelfde. Daardoor maakt het niet uit of een programma Python of Node.js nodig heeft. De server hoeft alleen Docker te kennen.

Het automatisch bouwen en deployen bij elke wijziging heet CI/CD (Continuous Integration / Continuous Deployment). Bij RWCrew doet GitHub Actions dat: zodra er een commit op develop of main binnenkomt, logt GitHub in op de server en zet het de nieuwe versie live (zie ).

Omgevingen: lokaal, test en productie

Dezelfde applicatie draait op meerdere plaatsen, elk met een eigen database en eigen instellingen. Zo'n plaats heet een omgeving:

  • Lokaal (development): op de pc van een ontwikkelaar, om te bouwen en te testen. Gegevens zijn proefgegevens.
  • Test (test.rwcrew.eu): een volledige kopie op de server, waar nieuwe functies eerst door echte gebruikers uitgeprobeerd worden. Je herkent ze aan een gekleurde banner "TEST".
  • Productie (rwcrew.eu): de echte applicatie met de echte gegevens.

Instellingen die per omgeving verschillen (databasewachtwoord, geheime sleutels, mailinstellingen) staan niet in de code maar in een omgevingsbestand (.env). Die bestanden staan nooit in Git, omdat ze geheimen bevatten.

Progressive Web App (PWA)

Een Progressive Web App is een website die zich op een telefoon gedraagt als een app: je zet ze via "Zet op beginscherm" met een eigen icoon op je telefoon, en ze opent schermvullend zonder adresbalk. Er is geen App Store of Play Store nodig, en een nieuwe versie van de website is meteen ook een nieuwe versie van de app. RWCrew gebruikt dit voor de telefoonversie onder het adres /m (zie ).
